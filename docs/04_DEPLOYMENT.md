| Requirement  | Minimum                    |
|--------------|----------------------------|
| PHP          | 8.1+ (8.2 recommended)     |
| MySQL        | 5.7+ / MariaDB 10.4+       |
| HTTPS        | required (SSL certificate) |
| `wp-content` | writable by PHP            |
| Disk         | ~1 GB free (uploads grow)  |

`max_execution_time=300`, `memory_limit=256M`.

## Step 0 — Export the database from the current environment

If the live/dev site still runs in Docker:

```bash
docker exec lylyrose-db mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers lylyrose > lylyrose.sql
```

> The dump contains live customer data (orders, users). Store it encrypted and
> delete it from any shared location right after importing.

## Step 1 — Get WordPress core on the host

On the server (or locally, then upload):

```bash
# VPS with WP-CLI (fastest path)
wp core download --locale=fa_IR --path=/var/www/yourdomain

# Shared hosting without SSH:
# 1. Download WordPress from https://fa.wordpress.org/download/
# 2. Upload via cPanel File Manager / FTP and extract in public_html/
```

Delete the default `wp-content/plugins` and `wp-content/themes` contents that
ship with WordPress if you want a lean tree (optional).

## Step 2 — Copy `wp-content` from this repo to the host

```bash
# From your machine (VPS over SSH)
rsync -av --exclude 'debug.log' wordpress/wp-content/ user@server:/var/www/yourdomain/wp-content/

# Or zip and upload via cPanel/FTP
zip -r wp-content.zip wordpress/wp-content -x "*/debug.log"
```

Make sure these runtime files do **not** get copied from a dev checkout (they
are regenerated by their plugins on the new host):
`advanced-cache.php`, `object-cache.php`, `wp-cache-config.php`.

## Step 3 — Migrate uploads

Uploads are not in git. Copy them from the current site:

```bash
docker cp lylyrose-wp:/var/www/html/wp-content/uploads ./uploads
# then rsync/scp ./uploads to <docroot>/wp-content/uploads
chown -R www-data:www-data wp-content/uploads   # adjust user on cPanel hosts
```

## Step 4 — Create the production database

cPanel: create a DB + user, grant ALL privileges.
VPS CLI:

```sql
CREATE DATABASE lylyrose DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'lylyrose_user'@'localhost' IDENTIFIED BY '<strong-password>';
GRANT ALL PRIVILEGES ON lylyrose.* TO 'lylyrose_user'@'localhost';
FLUSH PRIVILEGES;
```

## Step 5 — Import the dump

```bash
mysql -u lylyrose_user -p lylyrose < lylyrose.sql
```

## Step 6 — Create `wp-config.php`

Copy `wp-config-sample.php` (from the WordPress package) to `wp-config.php`
and set:

```php
define( 'DB_NAME',     'lylyrose' );
define( 'DB_USER',     'lylyrose_user' );
define( 'DB_PASSWORD', '<strong-password>' );
define( 'DB_HOST',     'localhost' );

// Force correct URLs (overrides whatever is in the DB)
define( 'WP_HOME',    'https://yourdomain.com' );
define( 'WP_SITEURL', 'https://yourdomain.com' );

// Salts: paste fresh values from https://api.wordpress.org/secret-key/1.1/salt/
```

> **Also set the table prefix**, which `wp-config-sample.php` does not contain —
> the installer normally appends it on first run. Importing a dump into a host
> whose config lacks it means WordPress looks at `wp_options` (prefix `wp_`),
> finds nothing, and redirects every request to `/wp-admin/install.php` even
> though every table is present.
>
> ```php
> $table_prefix = 'wp_';   // must match the prefix in the dump
> ```

Add hardening at the bottom, **above** `/* That's all… */`:

```php
define( 'DISALLOW_FILE_EDIT', true );
define( 'WP_POST_REVISIONS', 10 );
define( 'WP_MEMORY_LIMIT', '256M' );
define( 'FS_METHOD', 'direct' );          // direct updates if permissions allow
```

## Step 7 — Rewrite URLs inside the data

The dump was exported from `http://localhost:8020`. Replace every occurrence:

With WP-CLI (recommended):

```bash
wp search-replace 'http://localhost:8020' 'https://yourdomain.com' --all-tables --precise
wp search-replace 'http://yourdomain.com' 'https://yourdomain.com' --all-tables
wp cache flush
```

Without WP-CLI, install the [Better Search Replace](https://wordpress.org/plugins/better-search-replace/)
plugin, run the replacement for both URL forms (and any IP:port variants), then
delete the plugin.

Also verify in `wp_options`: `siteurl` and `home`.

| Plugin            | Change needed                                                        |
|-------------------|----------------------------------------------------------------------|
| Redis Object Cache| Deactivate on shared hosting (no Redis). On VPS: install redis-server, activate, verify "Connected". |
| WP Super Cache    | Revisit Settings → WP Super Cache; caching writes into `wp-config.php`/`.htaccess`. |
| UpdraftPlus       | Re-point remote storage (Google Drive/S3 credentials are per-site). |
| WP Mail SMTP      | Re-enter SMTP credentials; test with "Send a Test Email".           |
| ZarinPal / Gateland | Re-enter payment API keys (they were never in git — good).        |
| Persian SMS       | Update gateway API key + sender number.                             |
| Wordfence         | Run a scan after first load; check Firewall mode = learning → enabled. |
| WPS Hide Login    | Login stays at `/secure-login`; confirm it loads before announcing. |

## Step 9 — Cron

Docker used a sidecar container hitting `wp-cron.php`. On real hosting:

* **Shared hosting**: cron is usually fine as-is (WP triggers it itself).
* **Reliable scheduling**: disable WP's own trigger and add a real cron job.

In `wp-config.php`:

```php
define( 'DISABLE_WP_CRON', true );
```

Then a system crontab entry (every minute is standard; cPanel: Cron Jobs UI):

```bash
* * * * * cd /var/www/yourdomain && php -q wp-cron.php doing_wp_cron >/dev/null 2>&1
# or over HTTP:
* * * * * curl -sf https://yourdomain.com/wp-cron.php?doing_wp_cron >/dev/null 2>&1
```

## Step 10 — Web server config

Apache `.htaccess` (WordPress default, usually created automatically):

```apache
RewriteEngine On
RewriteRule ^index\.php$ - [L]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule . /index.php [L]
```

> On a cPanel addon domain the existing `.htaccess` holds only PHP-ini directives
> (`php_value`/`php_flag`); WordPress does not add its rewrite block there. The
> `# BEGIN WordPress … # END WordPress` block has to be appended **below** them,
> or every pretty permalink (`/shop/`, `/cart/`, `/checkout/`, `/my-account/`)
> returns 404 even though the `rewrite_rules` option is populated. Saving
> Settings → Permalinks only writes to the DB — it never creates the file.

Nginx (VPS):

```nginx
client_max_body_size 64m;
location / { try_files $uri $uri/ /index.php?$args; }
location ~ \.php$ { include fastcgi_params; fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name; }
```

Force HTTPS (top of `.htaccess` or in `wp-config.php`
`$_SERVER['HTTPS']='on';` behind a proper TLS terminator).

## Step 11 — Post-deploy checklist

```bash
wp core verify-checksums
wp plugin list --status=active
wp option get siteurl && wp option get home
wp db check
```

- [ ] Site loads over `https://` with valid certificate (no mixed content)
- [ ] Homepage renders Digikala theme RTL correctly
- [ ] **Shop, cart and checkout all return 200** — the home page alone does not prove
      permalinks work; a missing `.htaccess` rewrite block fails only these
- [ ] Product pages show Toman prices in Persian digits
- [ ] Cart → Checkout works end-to-end (place one real test order)
- [ ] ZarinPal/Gateland sandbox→live keys active; test payment round-trips
- [ ] `/secure-login` opens admin; `wp-login.php` redirects away
- [x] Passwords changed from dev values — **verified 2026-09-26** against production:
      `admin/admin123` is rejected.
- [ ] Wordfence scan clean; Limit Login Attempts active
- [ ] Emails send (new order notification)
- [ ] UpdraftPlus backup runs once successfully
- [ ] Torob feed / SEO sitemap reachable (`sitemap_index.xml`)
- [ ] Delete `lylyrose.sql` from everywhere it touched
- [ ] No helper scripts left in the webroot (SQL importer, `.dbpass`, `diag.php`, …)

## Rollback

Keep the pre-migration tarball of old `wp-content` and DB dump for 48h:

```bash
tar -czf rollback-pre-deploy.tar.gz /var/www/yourdomain/wp-content
mysqldump -u root -p lylyrose_pre > rollback.sql   # snapshot taken before import
```
